# A 股分位观测站数据库存储方案

## 一、当前项目位置

本项目位于个人网站仓库的 `backend` 目录：

```text
/www/wwwroot/www.11251236.xyz/personal-website/backend
```

相关文件：

```text
backend/
├── init.sql                         # 数据库建表脚本
├── common/                          # 配置和数据库连接
├── crawler/fetch_val.py             # 抓取并写入数据库
├── web/                             # FastAPI 查询服务
├── requirements.txt                 # 后端完整依赖
├── crawler/requirements.txt         # 爬虫依赖
└── web/requirements.txt             # Web 服务依赖
```

## 二、推荐结论

建议使用宝塔中安装的 **MySQL 8.x 或 MariaDB**，将 CSV 改为“数据库主存储，CSV 可选导出备份”。

原因：

- 宝塔对 MySQL/MariaDB 有成熟的图形化管理和备份功能。
- 后续制作网页、查询历史数据、增加指数或告警时更容易扩展。
- 当前数据量很小，不需要 Redis、PostgreSQL 或复杂架构。
- Python 可使用 `PyMySQL` 连接数据库，改造成本较低。

如果项目只供个人使用、没有网页并且追求最少维护，SQLite 也够用；但既然计划长期部署在服务器上，优先选择宝塔管理的 MySQL/MariaDB。

## 三、建议架构

```text
宝塔计划任务
    -> Python 抓取脚本
    -> MySQL/MariaDB
    -> 可选：导出 CSV
    -> 宝塔数据库备份
```

数据库建议命名为：

```text
cn_index_percentile
```

数据库用户建议单独创建，只授予该数据库的增删改查权限，不使用 root 连接程序。

## 四、建议表结构

根据当前项目的实际需求，采用两张精简业务表：

### 1. `index_info` 指数基本信息表

| 字段         | 类型            | 说明                      |
| ------------ | --------------- | ------------------------- |
| `id`         | BIGINT UNSIGNED | 自增主键                  |
| `index_code` | VARCHAR(16)     | 指数代码，例如 `SH000300` |
| `index_name` | VARCHAR(32)     | 指数名称，例如“沪深300”   |

关键约束：

```sql
UNIQUE KEY uk_index_code (index_code)
```

### 2. `index_valuation` 每日估值历史表

| 字段            | 类型            | 说明                        |
| --------------- | --------------- | --------------------------- |
| `id`            | BIGINT UNSIGNED | 自增主键                    |
| `index_code`    | VARCHAR(16)     | 指数代码，关联 `index_info` |
| `data`          | DATE            | 估值数据对应的完整日期      |
| `pe_percentile` | DECIMAL(8,6)    | PE历史百分位，保存原始小数  |
| `pb_percentile` | DECIMAL(8,6)    | PB历史百分位，保存原始小数  |

关键约束：

```sql
UNIQUE KEY uk_index_data (index_code, data)
```

`data` 使用完整日期，例如 `2026-09-08`。接口的 `date` 只有 `MM-DD`，应根据 `ts` 转换后再写入数据库。

同一指数同一天重复执行时，使用 `INSERT ... ON DUPLICATE KEY UPDATE` 更新记录，不会产生重复数据。

百分位建议保存为 `0.8656`，展示时再格式化为 `86.56%`。不要只保存带 `%` 的字符串，否则后续排序、绘图和统计会不方便。

## 五、当前脚本实现

当前 `backend/crawler/fetch_val.py` 已经使用 MySQL 作为主存储，主要行为如下：

1. 从 `backend/.env` 或生产环境变量读取数据库配置。
2. 请求丹卷基金接口并校验返回结构。
3. 将接口返回的百分位保存为数值，而不是格式化后的百分号字符串。
4. 使用 `(index_code, data)` 作为唯一键，执行幂等写入。
5. 接口数据缺失或异常时不写入半成品记录，并返回非零退出码。
6. 在一个事务中写入三条指数记录，失败时回滚。
7. 每次成功写入后输出日期、指数代码和两个百分位，方便宝塔日志检查。
8. CSV 仅作为可选导出或人工核对格式，不作为主数据源。

推荐的写入逻辑：

```text
请求接口
  -> 校验响应结构和最新交易日期
  -> 校验四个指标均为有效数值
  -> 开启事务
  -> 按 index_code + data 插入或更新
  -> 提交事务
  -> 输出成功日志
```

## 六、宝塔部署建议

### 数据库

在宝塔“数据库”中：

1. 创建数据库 `cn_index_percentile`。
2. 创建独立用户，例如 `cn_index_percentile_app`。
3. 设置强密码，并限制访问地址为 `127.0.0.1`（脚本和数据库在同一台服务器时）。
4. 字符集选择 `utf8mb4`。
5. 不给应用用户授予全局权限。

### Python 依赖

服务器应使用项目虚拟环境安装项目依赖：

```bash
/www/wwwroot/www.11251236.xyz/personal-website/backend/.venv/bin/python -m pip install -r /www/wwwroot/www.11251236.xyz/personal-website/backend/requirements.txt
```

当前依赖文件已经固定主要版本：

```text
backend/requirements.txt
backend/crawler/requirements.txt
backend/web/requirements.txt
```

### 宝塔计划任务

继续使用每日 22:00 主任务和 23:00 补偿任务。计划任务应：

- 使用绝对 Python 路径。
- 进入 `backend` 目录后使用模块方式运行 `crawler.fetch_val`。
- 将标准输出和错误输出写入日志。
- 不把数据库密码直接写在命令行中。

数据库密码建议通过项目目录外的环境文件、宝塔环境变量或受限权限的配置文件提供，并确保配置文件不提交到 Git、不放在可公开访问的 Web 目录中。

## 七、备份和恢复

数据库上线后，CSV 备份不能替代数据库备份。建议：

- 每日自动执行 `mysqldump` 或使用宝塔数据库备份。
- 至少保留 30 天备份，重要数据可保留 90 天。
- 备份文件不要放在网站公开目录。
- 定期做一次恢复测试，确认备份确实可用。
- CSV 可以作为面向人工查看的导出文件，不作为唯一数据源。

## 八、实施顺序

### 第一阶段

- 在宝塔创建 MySQL/MariaDB 数据库和专用用户。
- 建立 `index_info` 和 `index_valuation` 表及唯一索引。
- 先用测试库验证插入、重复执行和更新逻辑。

### 第二阶段

- 修改 Python 脚本接入数据库。
- 增加网络重试、接口结构校验、指标完整性校验。
- 让脚本在失败时返回非零状态并写明原因。

### 第三阶段

- 配置宝塔计划任务和数据库备份。
- 连续观察一周，确认每天每个指数只有一条对应日期记录。
- 根据需要增加网页查询、CSV 导出或告警功能。

## 九、最终建议

当前项目最适合采用：**宝塔 MySQL/MariaDB + Python 定时抓取 + 交易日期唯一约束 + 宝塔自动备份**。

CSV 不必立即废弃，可以作为导出和人工核对格式；数据库作为唯一主数据源。最重要的技术点是不要保存格式化百分号字符串、必须设置 `(index_code, data)` 唯一索引、重复运行必须更新而不是插入重复记录，并且数据库密码不能写死在代码中。
